# Крайние случаи и их обработка

## 1. Пользователь оффлайн

Сценарий: у пользователя нет интернета в момент обнаружения задержки рейса

Решение:
- Уведомления сохраняются в очередь в MongoDB с TTL 7 дней
- При восстановлении соединения отправляются все накопленные уведомления
- В мобильном приложении используется локальный кэш для отображения актуального статуса поездки
- Если пользователь не вышел в сеть за 7 дней - уведомление удаляется, но данные о поездке сохраняются

## 2. Нет доступных альтернативных рейсов

Сценарий: все рейсы по маршруту отменены или расписание не позволяет найти замену в разумные сроки

Решение:
- Уведомить пользователя о ситуации с объяснением причин
- Предложить альтернативные варианты: другой аэропорт вылета, другой день, другой вид транспорта (поезд)
- Автоматически инициировать процесс возврата средств через сервис бронирования
- Предложить связаться с поддержкой для индивидуального решения

## 3. Задержка данных от внешнего API

Сценарий: API авиакомпании не отвечает или возвращает устаревшие данные

Решение:
- Использовать polling каждые 5 минут как fallback к webhook
- Кэшировать последние известные статусы в Redis с TTL 30 минут
- При отсутствии данных более 1 часа - отправить пользователю уведомление о возможной задержке информации
- Иметь резервный источник данных (например, FlightAware как backup к API конкретной авиакомпании)

## 4. Конфликт расписаний при замене

Сценарий: альтернативный рейс пересекается с другим рейсом в рамках той же поездки

Решение:
- При подборе альтернативы проверять весь маршрут поездки, а не только один рейс
- Учитывать минимальное время пересадки (MCT) для каждого аэропорта
- Если конфликт неизбежен - предложить перестроить весь маршрут, а не только один сегмент
- Показать пользователю компромиссы: более ранний вылет с долгой пересадкой vs более поздний с короткой

## 5. Визовые ограничения

Сценарий: альтернативный маршрут проходит через страну, где требуется транзитная виза

Решение:
- Хранить информацию о гражданстве пользователя (из паспортных данных)
- Интегрироваться с базой визовых требований (например, IATA Timatic)
- Исключать из выдачи варианты, требующие визы, которой нет у пользователя
- Если альтернатива требует визы - явно предупредить пользователя и предложить только безвизовые варианты

## 6. Багажные ограничения

Сценарий: альтернативный рейс другой авиакомпании, нет interline agreement

Решение:
- Проверять наличие interline agreement между авиакомпаниями
- Если трансфер багажа невозможен - предупредить пользователя
- Предложить варианты с той же авиакомпанией или с partner airlines
- В крайнем случае - предложить рейс с пересадкой, где пользователь сам заберёт и сдаст багаж (с запасом времени)

## 7. Многопользовательская поездка (семья/группа)

Сценарий: в поездке несколько человек с разными предпочтениями

Решение:
- Уведомление отправляется всем участникам группы
- Для выбора альтернативы требуется согласие всех (или лидера группы)
- Учитывать разные паспортные данные при проверке виз
- Если кто-то из группы не может лететь альтернативным рейсом (виза, здоровье) - предложить раздельные варианты

## 8. Удаление паспортных данных

Сценарий: пользователь удалил аккаунт или поездка завершена

Решение:
- При завершении поездки устанавливается deletion_date = end_date + 24 часа
- Фоновая задача ежедневно удаляет просроченные записи
- При удалении аккаунта - немедленное удаление всех связанных паспортных данных
- Логи системы хранят только обезличенные идентификаторы, без персональных данных
